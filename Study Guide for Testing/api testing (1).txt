2XX: Success (Got it, done successfully).
4XX: Client Error (You made a mistake, like a bad URL or wrong data format)
5XX: Server Error (The server crashed or messed up).

200 OK: The standard success response for fetching data.
201 Created: The request succeeded and resulted in a new resource being made.
204 No Content: The request was successful, but there is no data to send back in the response body.

400 Bad Request: You hit the right destination, but the message you sent was malformed. This happens if your JSON has a syntax error (like a missing comma or quote) or if you miss a strictly required field.
404 Not Found: You knocked on the wrong door. The server is working fine, but the URL path does not exist on that server. This is usually caused by a typo in the URL or a deleted route.
401 Unauthorized: Correct. You need a valid login token/access key.
403 Forbidden: Correct. This is an ACL (Access Control List) or Role-Based access issue. You are logged in, but your role doesn't have the clearance.
422: Wrong Data Content or Data Type (e.g., sending text when a number is required, or failing validation rules).

200/201: Success (Data fetched / Resource created)204: Success, but no content to send back (like a delete action) 400: Bad Request (Syntax error/broken JSON) 401: Unauthorized (Needs a login/access token) 403: Forbidden (ACL/Role clearance block)404: Not Found (Wrong URL or route)422: Validation Error (Wrong data type or failed validation rules) 500: Internal Server Error (Backend app completely crashed) 502: Bad Gateway (Backend app server is not on/turned off) 504: Gateway Timeout (Backend took too long to respond)

RPC stands for Remote Procedure Call. In RPC, the client calls a function or procedure on the server almost like calling a local function — usually through a single HTTP method, POST, and the function name along with its parameters is passed in the request body. The server then uses the ORM to get the data from the database and returns the response back to the client. For example, in Odoo's RPC API, I used execute_kw and passed the method name and arguments to perform actions.

REST, on the other hand, is resource-based rather than function-based. It uses standard HTTP methods -> GET, POST, PUT, PATCH, DELETE - each mapped to a specific operation on a resource. This makes REST more structured and standardized compared to RPC, where the logic is wrapped inside function calls.


In Odoo RPC API testing, we hit the endpoint URL — for example /web/dataset/call_kw — using a POST request. In the request body, we pass data in JSON format, which includes the model name, the method name like create or write, and the field values including relational fields like One2many and Many2many. The ORM picks this up, connects to the PostgreSQL database, and executes the operation. In the response, we get the newly generated record ID — which confirms the record was successfully created. I used to validate this ID in Postman to confirm the test passed.


*API Headers*

Headers allow the client (e.g., your browser or application) and the server to communicate behind the scenes. 
They generally cover four core functions: 
Authentication: Proving who you are to access private data.
Content Negotiation: Defining the format of the data being exchanged.
Caching & Performance: Telling the system how long it can save and reuse data to save time and bandwidth.
Security & Restrictions: Managing domain permissions and traffic limits
